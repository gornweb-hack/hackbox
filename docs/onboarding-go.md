# Старт для Go-разработчика

Инструкция для двух Go-разработчиков. Шаги 0–9 у них общие, различается только предметная часть (раздел 10):

| Модуль | Кто | Что делает | Порт для отладки |
|---|---|---|---|
| `scenarios` | Go-1 | движок сценариев: прохождение, таймеры, две шкалы, концовки, разбор решений | 8101 |
| `gamification` | Go-2 | очки компетенций, уровни, ачивки, рейтинг, уведомления | 8102 |

Python-разработчику — [onboarding-python.md](onboarding-python.md).

## 0. Подготовить машину

- Git, Docker Desktop (запущен, «Engine running»), актуальная стабильная версия Go.
- VS Code с расширениями Go и Docker.
- Доступ к репозиторию `gornweb-hack/hackbox`.

## 1. Поднять проект (≈15 минут)

```bash
git clone git@github.com:gornweb-hack/hackbox.git
cd hackbox
docker compose up -d --build
```

- Откройте http://127.0.0.1:3000 и войдите под `user` / `user123`.
- Если порт занят другим проектом, скопируйте `.env.example` в `.env` и поменяйте порт.
- Подробности запуска — в [README](../README.md).

## 2. Прочитать (≈30 минут)

1. [README](../README.md) — как устроен проект: ядро, вход, события, база.
2. [AGENTS.md](../AGENTS.md) — правила работы, особенности версий. Нужны и вам, и ИИ-помощнику.
3. [Контракт модуля](module-contract.md) — **главное**: что обязан уметь ваш сервис.
4. `core/src/events/events.consumer.ts` — работающий образец цикла чтения событий. Go-версия пишется по нему.

## 3. Договориться с командой (первый созвон, ≈1 час)

- **Формат сценария (YAML).** Узлы, варианты ответа, эффекты на «лояльность» и «безопасность», таймер и ветка на случай, если время истекло, условия переходов, тексты разбора. Ведёт Go-1: это контракт между движком, фронтом и геймификацией.
- **API для фронта.** Эндпоинты, запросы и ответы.
- **События.** Главное — `scenario.completed`: Go-1 его публикует, Go-2 и Python-разработчик читают. Черновик для обсуждения:
  ```json
  {"runId": "uuid", "scenarioId": "conflict-seat", "outcome": "good",
   "loyalty": 72, "safety": 85, "timeouts": 1, "durationSec": 184,
   "competencies": {"conflict": 4, "standards": 2},
   "decisions": [{"nodeId": "n1", "choiceId": "check", "timedOut": false, "loyaltyDelta": 10, "safetyDelta": 5}]}
  ```
  В конверте события должен быть `userId` проводника. Итоговый формат записать в таблицу стандартных событий в контракте.

## 4. Зарегистрировать модуль

Если это ещё не сделал техлид одним коммитом за всех:

1. **Список модулей.** В `docker-compose.yml` в `x-modules` заменить заглушки: `tpl_go,tpl_py` → `scenarios,gamification,analytics`. При следующем `up` база сама создаст схему `<name>` и роль `<name>_svc`. Ядро покажет модули в админке со статусом «недоступен», пока их нет, и это не ошибка.
2. **Таблица портов.** В контракте заменить `tpl_go` и `tpl_py` на реальные имена и порты.
3. **Блок сервиса.** Раскомментировать пример в конце `services:` в `docker-compose.yml` — **только вместе с первым `Dockerfile`**. Если блок есть, а папки ещё нет, `docker compose up` сломается у всех.
   ```yaml
     scenarios:
       <<: *module
       build: ./modules/scenarios
       environment:
         PORT: "8080"
         DATABASE_URL: postgres://scenarios_svc:module_pass@postgres:5432/app
         REDIS_URL: redis://:redis_pass@redis:6379
       ports:
         - "127.0.0.1:8101:8080"
   ```

`docker-compose.yml` и контракт — общие файлы. Перед правкой сделайте `git pull`, а правку сразу закоммитьте и сообщите команде.

## 5. Скелет модуля — сначала контракт, потом логика

**Рекомендуемый стек.** Это не обязательство, но актуальную версию каждой библиотеки проверьте на pkg.go.dev.
- chi и huma v2 — роутинг, валидация и `/openapi.json` прямо из кода;
- pgx v5 (`pgxpool`) — база;
- goose v3 — миграции, встроенные в бинарник через `embed`;
- go-redis v9 — события;
- `log/slog` — логи в stdout.

**Структура** (предложение):
```
modules/scenarios/
  cmd/server/main.go   запуск, graceful shutdown по SIGTERM
  internal/httpapi/    роуты, чтение X-User-Id/X-User-Role, формат ошибок
  internal/db/         pgxpool, миграции goose при старте
  internal/events/     публикация и цикл чтения
  internal/engine/     предметная логика (у gamification — свой пакет)
  migrations/*.sql
  Dockerfile
```

**Чек-лист контракта** — пройти по порядку:
1. Сервис слушает `:$PORT` (в compose — 8080).
2. `GET /health` → `200 {"status":"ok"}`, если `pool.Ping` прошёл, иначе `503`.
3. `GET /openapi.json`. Huma отдаёт его по умолчанию, документацию — на `/docs`.
4. Подключение из `DATABASE_URL`. Миграции goose применяются при старте, таблицы пишутся без префикса схемы: `search_path` у роли уже настроен.
5. Если эндпоинту нужен пользователь, а `X-User-Id` нет, — `401`. Не та роль из `X-User-Role` — `403`.
6. Все ошибки — `{"code":"NOT_FOUND","message":"…"}`, валидация — `422 VALIDATION_ERROR`. Huma по умолчанию отдаёт другой формат (RFC 9457): переопределите `huma.NewError`.
7. JSON в camelCase — через теги `json:"userId"`. Время — `time.Now().UTC()`. Идентификаторы — UUID. Списки — `{"items": [...], "total": N}`.
8. У всех исходящих вызовов есть таймаут (`context.WithTimeout`). Если база при старте недоступна, лучше завершиться с ошибкой: Docker перезапустит сервис сам.

**Dockerfile:**
```dockerfile
FROM golang:1-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

FROM alpine:3
COPY --from=build /app /app
EXPOSE 8080
CMD ["/app"]
```

## 6. События в Go

Алгоритм — в разделе «События» [контракта](module-contract.md#события-если-модулю-они-нужны). С go-redis v9 он ложится так:

| Шаг | Вызов |
|---|---|
| публикация | `XAdd` в стрим `events`, `MaxLen: 10000`, `Approx: true`, поля `type` и `event` (JSON конверта) |
| группа при старте | `XGroupCreateMkStream(ctx, "events", "<name>", "$")`, ошибку `BUSYGROUP` игнорировать |
| чтение | `XReadGroup` с `Streams: {"events", ">"}`, `Count: 10`, `Block: 5s`. `redis.Nil` означает, что за 5 с ничего не пришло |
| успех | `XAck` |
| повторы раз в 30 с | `XPendingExt` с `Idle: 30s`, затем `XClaim` по каждому id. Если `RetryCount >= 5`, отправить в `events:dlq` с полями `error`, `group`, `sourceId` и сделать `XAck` |

- Имя consumer — `os.Hostname()`.
- Обработчики идемпотентны: одно событие может прийти дважды, повтор отсекается по `id` конверта или по `runId`.
- Публикация — «лучшее усилие»: если Redis лежит, основной запрос пользователя не должен падать, достаточно записи в лог.
- Уведомление проводнику — событие `notification.requested` с его `userId` и `data: {title, message, level}`. Тост в браузере покажет ядро.
- Типизированные методы go-redis сами разбирают ответ. Если пишете сырыми командами через `Do`, учтите, что Redis 8 может ответить в форме RESP3 (см. AGENTS.md). В любом случае проверьте цикл на живом Redis.

## 7. Проверить интеграцию

```bash
docker compose up -d --build scenarios
```
- `http://127.0.0.1:8101/health` → 200. Это модуль напрямую.
- В админке фронта (или на `http://127.0.0.1:4000/api/modules`) модуль в статусе «работает» не позже чем через 5 секунд.
- `http://127.0.0.1:3000/api/m/scenarios/<путь>` → ваш эндпоинт через ядро. В браузере после входа `X-User-Id` приходит сам.
- Если опубликовать `notification.requested` со своим `userId`, в браузере появится тост.
- Своя группа читателей видна так:
  ```bash
  docker compose exec redis redis-cli -a redis_pass --no-auth-warning XINFO GROUPS events
  ```

## 8. Цикл разработки

- **Быстро — нативно.** Если модуль уже есть в compose, остановите контейнер: `docker compose stop scenarios`. Запуск в PowerShell:
  ```powershell
  $env:PORT="8101"; $env:DATABASE_URL="postgres://scenarios_svc:module_pass@localhost:5432/app"; $env:REDIS_URL="redis://:redis_pass@localhost:6379"; go run ./cmd/server
  ```
  Порт базы — `POSTGRES_PORT` из вашего `.env`. Запросы шлите прямо на `:8101`, пользователя подставляйте сами: `curl.exe -H "X-User-Id: <uuid>" -H "X-User-Role: USER" ...`.
- **Через ядро с нативным модулем.** Нужен локальный файл `docker-compose.override.yml`, его не коммитить:
  ```yaml
  services:
    core:
      environment:
        MODULE_URL_SCENARIOS: http://host.docker.internal:8101
  ```
  После него выполнить `docker compose up -d core`.
- **Интеграция** — в контейнере: `docker compose up -d --build scenarios`. Логи — `docker compose logs -f scenarios`.

## 9. Git и самостоятельность

- Свой код — только в своей папке `modules/<name>/`.
- **ИИ-помощник работает в зоне Go** ([AGENTS.md](../AGENTS.md), раздел «Зоны ответственности агента»). Он правит только Go-модули, а `core/`, `web/` и Python-модуль только читает. Если нужна правка в ядре или на фронте, агент опишет, что поменять, а вы передадите это владельцу.
- `git pull` — несколько раз в день. Коммиты маленькие и осмысленные: `feat(scenarios): add timer timeout branch`. Жюри смотрит историю.
- **Понимайте каждую строку.** ИИ как помощник можно, но на защите попросят за пару минут поменять развилку или правило и объяснить, почему движок устроен так.
- Тесты на предметную логику (табличные) — это и страховка при правках, и аргумент на защите.
- Данные только синтетические, никаких реальных ФИО и табельных номеров.

## 10. Задачи на первый день

**Go-1 — `scenarios`:**
1. Модуль в статусе «работает» в админке.
2. Один сценарий из YAML проходится через API:
   - `POST /runs {scenarioId}` → первый узел;
   - `POST /runs/{id}/choices {choiceId}` → сервер сам проверяет, не истёк ли таймер, применяет эффекты к обеим шкалам и отдаёт следующий узел или финал;
   - `GET /runs/{id}/report` → разбор каждого решения.
3. Неверный или повторный выбор и выбор после финала дают понятные ошибки 4xx.
4. В финале публикуется `scenario.completed` — с этого момента Go-2 и Python-разработчик получают данные.
5. Живая правка при жюри: сценарии лежат в папке, которая монтируется в контейнер (`volumes` в compose), и перечитываются без пересборки. Тогда правка развилки занимает минуту.

**Go-2 — `gamification`:**
1. Модуль в статусе «работает».
2. Подписка на `scenario.completed`: начисление очков компетенций, повтор отсекается по `runId`.
3. Уровни и ачивки — по правилам из YAML, чтобы их тоже можно было поправить при жюри.
4. `GET /leaderboard` и `GET /me/progress` для фронта.
5. При новой ачивке — `notification.requested` проводнику.

   Имена для рейтинга: держать копию из событий `user.created` и `user.updated` или отдавать фронту только `id` (он подпишет через `/api/users?ids=`). Рейтинг по бригаде и депо появится, когда ядро начнёт хранить оргструктуру; до этого — по компании.
6. Позже: сгорание баллов (периодическая задача и уведомление) и челленджи.
