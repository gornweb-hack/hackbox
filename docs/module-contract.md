# Контракт модуля

Модуль — отдельный сервис на любом языке. Здесь перечислено всё, что он обязан уметь, чтобы ядро и фронт с ним работали. Фреймворк и структура кода — на усмотрение владельца. Как подключить модуль к проекту, описано в [README](../README.md#модули).

## Имя

Одно имя на всё: папка `modules/<name>`, сервис в [docker-compose.yml](../docker-compose.yml), схема и роль в базе, путь `/api/m/<name>/` у ядра.

Формат `^[a-z][a-z0-9_]*$`, нельзя `core`, `public`, `pg`, `pg_*`.

| Модуль | Порт для отладки |
|---|---|
| `tpl_go` | 8101 |
| `tpl_py` | 8102 |
| следующий | 8103 и дальше по порядку |

## Обязательно

1. **Запуск.** `Dockerfile` лежит в `modules/<name>/`. Сервис слушает `0.0.0.0:$PORT` (в compose `PORT=8080`). Настройки берутся только из переменных окружения.

2. **`GET /health`** отвечает `200 {"status":"ok"}`, когда модуль готов работать, включая связь с базой, если она нужна. Иначе `503`. Ответ быстрый, без тяжёлой логики: ядро опрашивает его и скрывает модуль, который не отвечает.

3. **`GET /openapi.json`** отдаёт спецификацию API, сгенерированную из кода: FastAPI делает это сам, в Go — [huma](https://huma.rocks). По ней фронт генерирует типы.

4. **API.** Пути любые, кроме `/health` и `/openapi.json`. Фронт вызывает `/api/m/<name>/<путь>`, ядро отрезает префикс, и модуль получает `/<путь>`.

5. **Пользователь.** Ядро проверяет вход и передаёт два заголовка: `X-User-Id` (UUID) и `X-User-Role` (`USER`, `MANAGER` или `ADMIN`). Модуль им доверяет: ядро вырезает эти заголовки из запросов клиента.
   - Запрос без входа приходит без этих заголовков. Если эндпоинту нужен пользователь, модуль отвечает `401`. Если нужна определённая роль, а её нет, модуль отвечает `403`.
   - На просроченный или плохой токен отвечает само ядро (`401 TOKEN_EXPIRED` или `TOKEN_INVALID`), до модуля такой запрос не доходит.
   - Имена пользователей модуль берёт не из своей базы: фронт получает их из `GET /api/users?ids=…`. Модуль хранит только `user_id`.

6. **JSON.** Поля в camelCase, даты в ISO 8601 и UTC (`2026-09-25T12:00:00Z`), идентификаторы — UUID. Список отдаётся как `{"items": [...], "total": 42}`.

7. **Ошибки.** HTTP-статус и тело:
   ```json
   {"code": "NOT_FOUND", "message": "Заметка не найдена"}
   ```
   `code` пишется в UPPER_SNAKE_CASE, по нему фронт решает, что делать. `message` — для человека. Ошибка валидации — `422` с `"code": "VALIDATION_ERROR"`. У FastAPI, huma и Nest формат ошибок по умолчанию другой, нужен свой обработчик.

8. **База.**
   - Подключение из `DATABASE_URL` под своей ролью `<name>_svc`.
   - `search_path` роли уже указывает на свою схему, поэтому таблицы пишутся без префикса.
   - Чужие схемы недоступны. Чужие данные берутся через API их владельца.
   - Миграции свои (goose, Alembic и т. п.), применяются при старте сервиса.

9. **Надёжность.**
   - Если при старте база недоступна, модуль повторяет попытки или завершается с ошибкой: Docker перезапустит его сам (`restart: unless-stopped`).
   - Все исходящие HTTP-вызовы идут с таймаутом. Другой модуль доступен по `http://<имя>:8080` и в любой момент может не ответить.
   - По SIGTERM модуль завершается корректно.

10. **Логи** пишутся в stdout.

**Желательно:** писать в логи `X-Request-Id`, если ядро его передало. По нему легко найти один запрос в логах разных сервисов.

## События (если модулю они нужны)

События нужны для цепочек между модулями: «урок пройден → начислить баллы → уведомить сотрудника». Они идут через Redis Streams. Подключение к Redis берётся из `REDIS_URL`. Работающий образец на Nest лежит в `core/src/events/events.consumer.ts`, хелпер для своего языка пишется по нему и по правилам ниже.

**Стримы и конверт:**
- Все события пишутся в один стрим `events`: `XADD events MAXLEN ~ 10000 * type <тип> event <JSON-конверт>`.
- Конверт:
  ```json
  {"id": "uuid", "type": "points.awarded", "source": "points", "time": "2026-09-25T12:00:00Z",
   "userId": "uuid (необязательно)", "broadcast": false, "requestId": "…", "data": {…}}
  ```
  - `id` — новый UUID на каждое событие;
  - `source` — имя модуля;
  - `userId` — кому событие адресовано;
  - `broadcast: true` — событие для всех;
  - поля, которые не нужны, можно не передавать.
- Тип события — `<сущность>.<глагол в прошедшем времени>`: `lesson.completed`, `points.awarded`. Типы, которые используются в проекте, перечислены в таблице ниже, новые дописываются туда же.

**Чтение (у каждого модуля своя группа):**
1. При старте создать группу: `XGROUP CREATE events <name> $ MKSTREAM`. Ошибку `BUSYGROUP` игнорировать — группа уже есть. Имя consumer — hostname контейнера.
2. Цикл: `XREADGROUP GROUP <name> <hostname> COUNT 10 BLOCK 5000 STREAMS events >`.
3. Событие не того типа, который модуль обрабатывает, — сразу `XACK`. Обработано успешно — `XACK events <name> <id>`. Ошибка — без `XACK`: событие останется в ожидании.
4. Раз в 30 с — повторы:
   - `XPENDING events <name> IDLE 30000 - + 10` даёт `[id, consumer, простой, число доставок]`;
   - каждое событие забрать себе через `XCLAIM events <name> <hostname> 30000 <id>` и обработать снова;
   - если доставок уже 5, отправить в `events:dlq` (исходные поля плюс `error`, `group` и `sourceId`) и сделать `XACK`.
5. Запись, которую не удаётся разобрать, сразу уходит в `events:dlq`.
6. Если Redis недоступен (ошибка соединения или `NOGROUP`), подождать 2 с, пересоздать группу и продолжить.

Протокол Redis 8 может отдавать ответ `XREADGROUP` как `[stream, entries]` (RESP3), а не `[[stream, entries]]` (RESP2). Разбор должен понимать обе формы.

**Обязательно:**
- Обработчики идемпотентны: одно событие может прийти дважды, повтор отсекается по `id` или по смыслу («баллы за урок 3 уже начислены»).
- Публикация — «лучшее усилие». Если Redis лежит, основной запрос пользователя не должен падать: ошибка пишется в лог.
- Свои ключи в Redis — только с префиксом `<name>:` (например, рейтинг `points:leaderboard` — sorted set). Чужие ключи не трогать, общий только стрим `events`.

**Стандартные события:**

| Тип | Кто публикует | `data` | Что происходит |
|---|---|---|---|
| `notification.requested` | любой модуль | `{title, message, level: "info" \| "success" \| "warning", link?}` | ядро показывает уведомление в браузере. Нужен `userId` или `broadcast: true`, иначе событие уйдёт в DLQ |
| `user.created`, `user.updated` | ядро | `{id, name, role}` | модуль может держать у себя копию имён, например для рейтинга |

Любое событие с `userId` или `broadcast: true` ядро пересылает в браузер (SSE), и фронт может сразу обновить экран. Например, `points.awarded` с `userId` обновит счётчик баллов сотрудника без перезагрузки.

## Проверка своего модуля

Через ядро: модуль должен появиться в `http://127.0.0.1:4000/api/modules` со статусом `up`, а его API — отвечать на `http://127.0.0.1:4000/api/m/<name>/<путь>`.

Через ядро от имени пользователя: войдите демо-аккаунтом (см. [README](../README.md#вход)) и передайте `accessToken` в заголовке `Authorization: Bearer <токен>`. Ядро само подставит `X-User-Id` и `X-User-Role`.

Напрямую, в обход ядра, заголовки пользователя подставляются вручную:

```bash
curl -i http://127.0.0.1:8101/health
curl http://127.0.0.1:8101/openapi.json
curl -H "X-User-Id: 00000000-0000-0000-0000-000000000001" -H "X-User-Role: USER" http://127.0.0.1:8101/<путь>
```

В PowerShell вместо `curl` пишите `curl.exe`. Тело с кириллицей передавайте из файла в UTF-8 (`--data-binary "@body.json"`): в аргументах командной строки Windows её искажает.
