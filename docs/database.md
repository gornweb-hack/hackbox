# Работа с базой данных

Памятка для всех разработчиков и их ИИ-помощников. Коротко: одна база, одна схема `public`, одна роль ядра. Модули ядра делят схему, но у каждого свои таблицы, и в таблицы друг друга модули напрямую не пишут.

## Как устроено

- **Один Postgres 17**, одна база `app`. Сортировка по-русски (ICU `ru-RU`), `max_connections=300`.
- **Весь бэкенд — одно приложение**, ядро на Nest. Оно подключается ролью `core_svc` и работает в схеме `public`.

  | Роль | Схема | Пароль (dev) |
  |---|---|---|
  | `core_svc` | `public` | `core_pass` |

- **`core_svc` — владелец базы и может создавать базы.** Это нужно Prisma: `migrate reset` пересоздаёт схему, а `migrate dev` создаёт временную shadow-базу. Роль и владение настраивает `db-init` при каждом `docker compose up`, вручную ничего создавать не нужно.
- **Подключение** — из переменной `DATABASE_URL`:
  - из контейнера: `postgres://core_svc:core_pass@postgres:5432/app`;
  - с хоста: `postgres://core_svc:core_pass@localhost:<POSTGRES_PORT>/app` (порт по умолчанию 5432).
- **Код ходит в базу только через `PrismaService`.** Это глобальный модуль и одно подключение на всё приложение.

## Таблицы модулей

- **У каждого модуля ядра свои таблицы с префиксом модуля:** модель `ScenarioRun` → `@@map("scenario_runs")`. У входа и сотрудников — `users` и `refresh_tokens`.
- **Модули не пишут в таблицы друг друга напрямую.** Данные модуля меняет его сервис, сотрудников — `UsersService`.
- **Между модулями нет связей Prisma и JOIN.** Идентификатор из другого модуля хранится обычным полем с индексом, например `userId String @db.Uuid`. Связь Prisma потребовала бы полей в моделях обоих модулей и связала бы их намертво.
- **Данные другого модуля берутся:**
  - через его сервис: модуль отдаёт сервис через `exports`, экспорт добавляется, когда понадобился;
  - или через копию из событий (см. [памятку по событиям](events.md)).

Зачем так: модуль можно переделать или вынести в отдельный сервис, не ломая остальные.

## Правила для таблиц

- **Идентификаторы** — `uuid`. Prisma генерирует сортируемые по времени v7 сама: `@default(uuid(7))`.
- **Время** — `timestamptz`, всегда в UTC.
- **Имена** таблиц и колонок в базе — `snake_case` (`@@map`, `@map`), в коде и JSON — `camelCase`.
- **Защита от повторов.** Событие может прийти дважды, поэтому нужен уникальный ключ по его смыслу (`run_id` с `@unique`) и вставка, которая пропускает повтор.
- **Сначала коммит в базу, потом публикация события.** Иначе событие уйдёт о том, чего в базе нет.
- **Копия данных другого модуля может отставать** на доли секунды. Если нужной строки ещё нет, не падать: показать заглушку («Сотрудник») или пропустить.
- **Только синтетические данные:** никаких реальных ФИО, телефонов, табельных номеров (152-ФЗ, требование ТЗ).

## Миграции

- **Только Prisma 7.** Схема — `core/prisma/schema.prisma`, миграции — `core/prisma/migrations/`.
- **Новая миграция** — `npx prisma migrate dev --name <имя>` в `core/`. Нужен `DATABASE_URL` на локальную базу, например в `core/.env`.
- **Применение** — при каждом старте контейнера ядра (`prisma migrate deploy`).
- **Папка миграций одна на всю команду:**
  - перед созданием миграции — `git pull` и предупреждение команде;
  - миграции создаёт один человек за раз;
  - после создания — сразу коммит.
- **Уже применённую миграцию не редактировать:** её нужно не переписывать, а добавить новую.
- **Одна миграция — одно изменение**, коммит вместе с кодом, который её использует.

## Отладка

- Зайти в базу под суперпользователем, чтобы видеть всё:
  ```bash
  docker compose exec postgres psql -U postgres -d app
  ```
- Зайти под ролью ядра — так видно ровно то, что видит приложение:
  ```bash
  docker compose exec postgres psql -U core_svc -d app
  ```
- Внутри psql: `\dt` — таблицы, `\d <таблица>` — её колонки и индексы.
- В базах, созданных до перехода на один бэкенд, могут остаться пустые схемы `tpl_go` и `tpl_py` и роли `tpl_go_svc` и `tpl_py_svc`. Они ни на что не влияют. Удалять их — только с согласия человека.
- Снимок базы перед демо и полный сброс — в [README](../README.md#база-данных).

## Правила для ИИ-агентов

- **Не создавать связей Prisma и JOIN между модулями** и не писать в таблицы другого модуля напрямую: данные — через его сервис или копию из событий.
- **Не подключаться из кода суперпользователем `postgres`.**
- **Миграции** — только новые, по одной, в `core/prisma/migrations/`. Уже применённые не редактировать.
- **Команды, которые удаляют данные** (`docker compose down -v`, `DROP`, `TRUNCATE`, `prisma migrate reset`), — только с явного согласия человека. Проверки, которые портят данные, — во временной копии (`docker compose -p hbverify …`).
- **Роли и схемы не создавать вручную.**
- **Тестовые данные — только синтетические.**
