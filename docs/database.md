# Работа с базой данных

Памятка для всех разработчиков и их ИИ-помощников. Коротко: у каждого сервиса своя схема. Внутри неё можно всё, что умеет Postgres. В чужие схемы — ничего: ни внешних ключей, ни JOIN, ни запросов.

## Как устроено

- **Один Postgres 17**, одна база `app`. Сортировка по-русски (ICU `ru-RU`), `max_connections=300`.
- **У каждого сервиса своя схема и своя роль.** Роль владеет схемой, и `search_path` у неё уже указывает на свою схему, поэтому таблицы пишутся без префикса.

  | Сервис | Схема | Роль | Пароль (dev) |
  |---|---|---|---|
  | ядро | `public` | `core_svc` | `core_pass` |
  | модуль `<name>` | `<name>` | `<name>_svc` | `module_pass` |

- **Схему и роль создаёт `db-init`** при каждом `docker compose up` для каждого имени из `x-modules` в `docker-compose.yml`. Создавать их вручную не нужно.
- **Подключение** — только из переменной `DATABASE_URL`, под своей ролью:
  - из контейнера: `postgres://<name>_svc:module_pass@postgres:5432/app`;
  - с хоста: `postgres://<name>_svc:module_pass@localhost:<POSTGRES_PORT>/app` (порт по умолчанию 5432).

## Что можно и что нельзя

| | Внутри своей схемы | С чужой схемой (`public.*`, `<другой модуль>.*`) |
|---|---|---|
| таблицы, индексы, ограничения | да | нет |
| внешние ключи | да | нет — роль не видит чужую схему, база не пустит |
| JOIN, подзапросы | да | нет |
| транзакции | да | нет — это другой сервис |

Зачем так: модуль можно менять, мигрировать и ронять, не ломая остальных. JOIN в таблицу ядра связал бы модуль с ядром намертво.

## Как получить чужие данные

1. **Хранить чужой идентификатор как обычное поле, без внешнего ключа.** Например, `user_id uuid NOT NULL` с индексом, но без `REFERENCES`. `X-User-Id` приходит от ядра, которое уже проверило вход, поэтому ему можно верить.
2. **Держать у себя копию нужных чужих данных, обновляемую событиями.** Например, таблица `users_cache` (имя, роль, бригада, депо), которую наполняют события `user.created` и `user.updated`. Дальше — обычный JOIN внутри своей схемы.
3. **Спросить владельца данных через API** — для редких запросов: HTTP-вызов модуля или ядра с таймаутом. Или фронт сам собирает данные, например имена из `GET /api/users?ids=…`.

Копию меняют только события от владельца данных. Если нужно поменять сами данные (имя сотрудника, название сценария), это делает их владелец.

## Правила для таблиц

- Идентификаторы — `uuid`. Postgres 17 умеет только `gen_random_uuid()` (v4); если нужен сортируемый по времени v7, его генерирует код.
- Время — `timestamptz`, всегда в UTC.
- Имена таблиц и колонок — `snake_case`. В JSON ответов API — `camelCase`, преобразование делает код.
- Защита от повторов: событие может прийти дважды, поэтому нужен уникальный ключ по его смыслу (`run_id UNIQUE`) и `INSERT … ON CONFLICT DO NOTHING`.
- Сначала коммит в базу, потом публикация события. Иначе событие уйдёт о том, чего в базе нет.
- Копия чужих данных может отставать на доли секунды. Если нужной строки ещё нет, не падать: показать заглушку («Сотрудник») или пропустить.
- Пул соединений держать небольшим, 5–10 на сервис: база общая на всех.
- Только синтетические данные: никаких реальных ФИО, телефонов, табельных номеров (152-ФЗ, требование ТЗ).

## Миграции

У каждого сервиса свои миграции. Они лежат в его папке и применяются при старте сервиса. Служебная таблица версий ложится в свою схему сама — через `search_path`.

| Сервис | Инструмент | Где лежат | Как создать |
|---|---|---|---|
| ядро (Nest) | Prisma 7 | `core/prisma/migrations/` | `npx prisma migrate dev --name <имя>` в `core/`, нужен `DATABASE_URL` на локальную базу |
| Go-модуль | goose | `modules/<name>/migrations/*.sql`, встроены в бинарник через `embed` | `goose create <имя> sql`; версии — таймстемпы |
| Python-модуль | Alembic | `modules/<name>/migrations/` | `alembic revision -m "<имя>"`; схема URL — `postgresql+psycopg://` |

- Уже применённую миграцию не редактировать: её нужно не переписывать, а добавить новую.
- Одна миграция — одно изменение, коммит вместе с кодом, который её использует.

## Заметки по языкам

- **Go:** `pgxpool` для запросов и транзакций, goose для миграций. Строку `postgres://…` pgx принимает как есть.
- **Python:** SQLAlchemy 2 с psycopg 3 и Alembic. Схему URL из `DATABASE_URL` заменить на `postgresql+psycopg://`, иначе SQLAlchemy не подключится.
- **Nest:** Prisma 7 только через `@prisma/adapter-pg`, клиент импортируется из `src/generated/prisma/client.js` (подробнее — в [AGENTS.md](../AGENTS.md)).

## Отладка

- Зайти в базу под суперпользователем, чтобы посмотреть всё:
  ```bash
  docker compose exec postgres psql -U postgres -d app
  ```
- Зайти под своей ролью — так видно ровно то, что видит модуль:
  ```bash
  docker compose exec postgres psql -U <name>_svc -d app
  ```
- Внутри psql: `\dn+` — схемы и владельцы, `\dt <name>.*` — таблицы схемы.
- Снимок базы перед демо и полный сброс — в [README](../README.md#база-данных).

## Правила для ИИ-агентов

- **Работать только со своей схемой**: той, что соответствует зоне и модулю (см. [AGENTS.md](../AGENTS.md), раздел «Зоны ответственности агента»). Ядро — `public`, модуль — `<name>`.
- **Не создавать связей с чужими схемами:** внешние ключи, JOIN, подзапросы, представления, запросы к `public.*` из модуля или к схемам модулей из ядра. Если нужны чужие данные, использовать копию из событий или API — приёмы выше.
- **Не подключаться из кода сервиса суперпользователем `postgres`** и не выдавать права (`GRANT`) на чужие схемы, чтобы «просто заработало».
- **Миграции:** создавать только в папке своего сервиса; уже применённые не редактировать; миграции других сервисов не трогать.
- **Команды, которые удаляют данные** (`docker compose down -v`, `DROP`, `TRUNCATE`, `prisma migrate reset`), — только с явного согласия человека. Проверки, которые портят данные, — во временной копии (`docker compose -p hbverify …`).
- **Схемы и роли не создавать вручную.** Новый модуль появляется через `x-modules` в `docker-compose.yml` — это общий файл, правится только по просьбе человека.
- **Тестовые данные — только синтетические.**
