# Контент тренажёра

Сценарии и справочники лежат в [content/](../content/) в корне репозитория. Ядро читает их при каждом запросе, поэтому правка файла видна сразу, без пересборки и перезапуска. В Docker папка монтируется в контейнер ядра (`./content:/app/content:ro`), путь задаёт `CONTENT_DIR`.

## Файлы

| Файл | Что в нём |
|---|---|
| `content/categories.yaml` | справочник категорий: `id` и `title` |
| `content/scenarios/<id>.yaml` | один сценарий; `id` — имя файла, под ним сценарий приходит из API |
| `content/gamification.yaml` | уровни, опыт, репутация и ачивки |
| `content/skills.yaml` | навыки для радара и рекомендации |

## Поля сценария

| Поле | Обязательно | Что это |
|---|---|---|
| `title` | да | название |
| `summary` | да | одна фраза для главной карточки и каталога |
| `category` | да | `id` из `categories.yaml` |
| `carClass` | да | `Стандарт`, `Комфорт`, `Бизнес` или `Первый` — классы ВСМ по СТО РЖД 03.011 |
| `durationMin` | да | сколько минут идёт сценарий |
| `order` | да | порядок в каталоге, он же задаёт порядок категорий; первый сценарий предлагается новичку |
| `new` | нет | `true` — сценарий показывается на плашке «Новый сценарий» |

Пример — `content/scenarios/minute-stop.yaml`:

```yaml
title: Минутная стоянка
summary: Стоянка длится одну минуту, а пассажир хочет выйти подышать на платформу.
category: service
carClass: Стандарт
durationMin: 3
order: 4
new: true
```

## Диалог: узлы и переходы

Сам диалог — граф узлов: `start` — с какого узла начинается сценарий, `nodes` — узлы по `id`.

| Поле узла | Что это |
|---|---|
| `text` | реплика или описание ситуации |
| `choices` | варианты ответа; у финального узла их нет |
| `timer` | сколько секунд на решение; без поля — без таймера |
| `timeout` | что будет, если время вышло: `effects`, `review`, `to` |
| `final` | `good`, `ok` или `bad` — узел финальный, это исход прохождения |

| Поле варианта | Что это |
|---|---|
| `id` | уникален внутри узла |
| `text` | что говорит или делает проводник |
| `effects` | изменение шкал: `{loyalty: 10, safety: -20}` |
| `review` | разбор после финала: почему так и как можно было лучше |
| `skills` | необязательно: навыки, которые показывает этот вариант, `[acknowledge, safety]` — id из `skills.yaml` |
| `action` | необязательно: жест проводника в сцене прохождения — `radio`, `announce`, `water`, `pill`, `ticket`, `reach`, `point`, `calm`, `ignore`, `shout`. Незнакомый жест сцена пропускает и показывает реакцию по исходу решения |
| `to` | куда ведёт решение |

`to` — это `id` узла или список правил. Срабатывает первое правило, чьё условие выполнено. Последнее правило — без условия:

```yaml
to:
  - if: {safety: {below: 40}}   # безопасность ниже 40
    node: station
  - node: medics                # иначе
```

В условии бывают `below` («ниже») и `atLeast` («не ниже») по шкалам `loyalty` и `safety`.

Как считаются шкалы:
- в начале прохождения обе шкалы равны 50;
- `effects` прибавляются, результат обрезается до 0–100;
- условия перехода проверяются уже по изменённым шкалам;
- исход прохождения задаёт финальный узел.

Пример — первый узел `content/scenarios/sick-passenger.yaml`, сокращённо:

```yaml
start: alarm
nodes:
  alarm:
    text: >-
      Пассажирка машет вам: её соседу плохо…
    timer: 15
    timeout:
      effects: {loyalty: -10, safety: -25}
      review: >-
        Пока вы решали, пассажиру стало хуже…
      to: worse
    choices:
      - id: call-chief
        text: >-
          Подойти: «Я рядом, сейчас приглашу начальника поезда и организуем помощь»
        effects: {loyalty: 15, safety: 20}
        review: >-
          Верно и быстро — ровно так, как в памятке…
        to: medics
```

Если в тексте есть двоеточие с пробелом или он длинный, пишите его блоком `>-`, как в примере: так YAML не спутает двоеточие с новым полем.

## Правила геймификации

`content/gamification.yaml` — уровни, опыт, репутация и ачивки. Ядро читает файл при каждом запросе и пересчитывает прогресс всех сотрудников из журнала прохождений.

| Поле | Что это |
|---|---|
| `levels` | уровни по возрастанию: `speed` — скорость уровня (до 400 км/ч), подпись под его вагоном, `title` — титул, `xp` — порог опыта; у первого уровня порог 0 |
| `xp` | опыт за прохождение по исходу: `good`, `ok`, `bad` |
| `reputation.window` | репутация — среднее итоговых шкал за столько последних прохождений |
| `achievements` | ачивки: `id` латиницей, уникальный; `title`, `description` и ровно одно правило `when` |

Правила ачивок:

| `when` | Ачивка получена, когда |
|---|---|
| `{runs: 10}` | всего 10 прохождений |
| `{categories: 4}` | пройдены сценарии 4 разных категорий |
| `{run: {category: medical, outcome: good}}` | хотя бы одно прохождение подходит под все условия. Условия: `category`, `outcome` (`good`, `ok`, `bad`), `minLoyalty` и `minSafety` — итоговая шкала не ниже порога, `noTimeouts: true` — в прохождении были решения на время и ни одного таймаута |

Ачивка засчитывается тому прохождению, на котором условие выполнилось впервые. Разбор этого прохождения показывает её в награде, а проводник сразу получает тост «Ачивка: …». Правка правил пересчитывает полку и награды в разборах, но тост приходит только в момент прохождения.

Если `gamification.yaml` не читается, запросы геймификации отвечают `500 CONTENT_INVALID` с причиной.

## Навыки

`content/skills.yaml` — оси радара на главной. Первые четыре — шаги ролевой модели из памятки «Ситуации на борту»: признать ситуацию (`acknowledge`), обозначить правило (`rule`), предложить решение (`solution`), заверить (`reassure`). Ещё два — безопасность (`safety`) и хладнокровие (`composure`).

| Поле | Что это |
|---|---|
| `window` | процент считается по стольким последним прохождениям |
| `skills` | навыки по порядку осей радара: `id` и `title`; `timers: true` — навык без меток |

Как считается процент:
- узел проверяет навык, если его метка есть хотя бы у одного варианта в `skills`;
- решение верное, если выбран вариант с этой меткой; таймаут — неверное решение;
- навык с `timers: true` (хладнокровие) проверяет каждый узел с таймером, верно — ответить до таймаута;
- процент = верные решения / решения, где навык проверялся.

Слабый навык — с наименьшим процентом ниже 100%. Если все проверенные навыки на 100%, слабого нет, и главная карточка предлагает следующий непройденный сценарий. Иначе она предлагает сценарий, где он проверяется в наибольшем числе узлов; при равенстве — тот, что дольше не проходили. Метки читаются из YAML при каждом запросе, поэтому их правка сразу пересчитывает навыки у всех. Незнакомую метку ловит тест `core/src/analytics/content.spec.ts`.

## Правка при жюри

Название:
1. Откройте файл сценария, например `content/scenarios/minute-stop.yaml`, и поменяйте `title`.
2. Сохраните файл и обновите главную: новое название уже на плашке.

Развилка:
1. В `content/scenarios/sick-passenger.yaml` у варианта `call-chief` замените `to: medics` на `to: station`.
2. Сохраните файл и начните сценарий заново: после этого решения врачей среди пассажиров уже не ищут, сразу едут к станции.

Правило начисления:
1. В `content/gamification.yaml` поменяйте `good: 150` на `good: 300` или порог уровня `xp: 800` на `xp: 400`.
2. Сохраните файл и обновите главную: опыт и заполнение вагонов пересчитаны.

Порог ачивки:
1. В `content/gamification.yaml` у ачивки `marathon` поменяйте `runs: 10` на `runs: 3`.
2. Сохраните файл и обновите главную: у кого уже три прохождения, у того «Марафон» на полке, а «Следующая» сменилась.

Метка навыка:
1. В `content/scenarios/minute-stop.yaml` у варианта `warn` замените `skills: [rule]` на `skills: [rule, solution]`.
2. Сохраните файл и обновите главную: у тех, кто выбирал этот вариант, «Предложить решение» на радаре вырос, а рекомендация могла смениться.

Файл с ошибкой не ломает каталог. Он пропускается, а причина пишется в лог ядра (`docker compose logs core`), например `minute-stop.yaml: класс «Эконом» не из списка`. Если не читается `categories.yaml`, `GET /api/scenarios` отвечает `500 CONTENT_INVALID` с причиной.
