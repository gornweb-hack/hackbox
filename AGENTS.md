# Инструкции для ИИ-агентов

Этот файл читают Claude Code, Cursor, Codex, Copilot и другие агенты, которые работают в репозитории. Людям он тоже полезен как краткая памятка. Для Next.js есть отдельные правила в [web/AGENTS.md](web/AGENTS.md).

## Проект

hackbox — заготовка команды Gornweb для хакатонов:
- фронт на Next.js;
- бэкенд на Nest.js — одно приложение (ядро), собранное из модулей;
- Postgres и Redis Streams.

Всё поднимается через Docker Compose.

**Текущая задача** — кейс «Геймификация для ВСМ» (Хакатон Московского транспорта). Это тренажёр для проводников ВСМ-400:
- нелинейные сценарии с таймерами;
- две шкалы — «лояльность пассажира» и «рейтинг безопасности»;
- очки компетенций, ачивки, рейтинг по бригаде, депо и компании;
- разбор решений, аналитика компетенций, уведомления.

**Сдача — 27 сентября, 23:59 МСК.** Работающий сквозной сценарий важнее полноты функций.

Артефакты сдачи:
- репозиторий с осмысленной историей коммитов;
- прототип, который запускается по README;
- описание архитектуры (диаграммы);
- API (Swagger);
- User Flow с примерами сценариев;
- ограничения и план развития.

## Главное правило: ИИ — помощник, а не автор

Жюри отдельно оценивает, понимает ли команда свой код. Любой участник должен объяснить движок сценариев и начисление очков и за несколько минут поменять развилку сценария или правило шкалы. Мёртвый код, TODO-заглушки, выдуманные зависимости и разнобой стилей прямо снижают оценку. Поэтому:

- **Изменения — маленькие, под конкретную задачу.** Большие куски «на всякий случай» не генерировать.
- **Объяснять сделанное.** После изменения коротко сказать, что и почему сделано, чтобы человек мог пересказать это жюри.
- **Предметную логику не писать целиком за разработчика.** Это движок сценариев, правила шкал и очков, ачивки. Предлагать устройство, объяснять, писать по шагам вместе с человеком.
- **Без мусора в коде.** Никаких TODO-заглушек вместо логики, мёртвого кода и заделов «на будущее». То, что перестало использоваться, удалять.
- **Не выдумывать зависимости и API.** Прежде чем добавить пакет, проверить, что он существует и какая у него актуальная версия. Для новых мажорных версий читать документацию (раздел «Особенности версий»).
- **Писать в стиле соседнего кода:** те же библиотеки, именование, плотность комментариев.
- **Не коммитить и не пушить** — это делает человек. Предлагать сообщение коммита в формате Conventional Commits на английском, например `feat(scenarios): add timer timeout branch`.
- **Архитектурные изменения — только после согласия.** Новый сервис, новая зависимость, изменение контракта: сначала предложить и дождаться ответа.

## Бэкенд и фронтенд

Проект делят две команды:

| Часть | Где | Что внутри |
|---|---|---|
| **Бэкенд** | `core/`, `infra/`, `docker-compose.yml` | ядро на Nest: вход и сотрудники, события, база; предметные модули `scenarios` (движок сценариев), `gamification` (очки, уровни, ачивки, рейтинг), `analytics` (компетенции, пробелы, выводы) в `core/src/<name>/` |
| **Фронтенд** | `web/` | интерфейс на Next.js |

Как написать модуль ядра — [docs/onboarding.md](docs/onboarding.md).

**Свой модуль.** Так двое не правят одно и то же место и не тратят время на слияния.
- **В начале сессии** агент уточняет, над чем работает человек: модуль ядра (например, `core/src/scenarios`), остальное ядро или `web/`. Это его модуль на всю сессию.
- **Правки — в своём модуле.** Если задача требует изменить другой модуль ядра или другую часть проекта (`web/` для бэкенда и наоборот), агент не правит молча. Он останавливается, говорит, что и где нужно поменять, и предлагает написать коллеге. Правит только после того, как человек подтвердил, что договорился.
- **Без подтверждения можно:**
  - читать любой код;
  - вызывать экспортированные сервисы других модулей;
  - править общие файлы в части своего модуля: строку в `app.module.ts`, свой блок в `schema.prisma`, свои настройки в `config.ts`, `docker-compose.yml` и `.env.example`.
- **Изменился API** (новый эндпоинт, другой формат ответа, новое событие для браузера) — сообщить другой команде и обновить описание в README или `docs/`.

**Частые коммиты.** Конфликт после часа работы решается за минуту, после дня — за час.
- **В начале сессии** напомнить сделать `git pull`.
- **После каждого законченного шага** (работает, тесты зелёные) предложить коммит с готовым сообщением и `git push`.
- **Если незакоммиченного накопилось много** — `git status` показывает больше 5–7 изменённых файлов или несколько законченных шагов без коммита, — остановиться и предложить закоммитить, прежде чем продолжать.
- **Общие файлы** (`docker-compose.yml`, `.env.example`, `docs/`, `AGENTS.md`, `core/prisma/schema.prisma`, `core/src/app.module.ts`, `core/src/config.ts`, `package.json`): перед правкой — `git pull`, после — сразу коммит.
- **Миграции Prisma — по одной.** Перед `prisma migrate dev` предупредить команду бэкенда, после — сразу коммит.

## Устройство

| Сервис | Где | Стек | Порт на localhost |
|---|---|---|---|
| `web` | `web/` | Next.js 16, React 19, Tailwind 4, shadcn/ui (Base UI), TanStack Query | 3000 |
| `core` | `core/` | Nest.js 12 (ESM), Prisma 7, ioredis 6 | 4000 |
| `postgres` | `infra/postgres/` | Postgres 17, ICU `ru-RU` | 5432 (`POSTGRES_PORT`) |
| `redis` | — | Redis 8, AOF | 6379 (`REDIS_PORT`) |
| `db-init` | `infra/postgres/bootstrap.sh` | запускается при каждом `up`: роль ядра и владение базой | — |

- **Браузер ходит только на `web`.** Запросы `/api/*` Next проксирует в ядро через rewrites, поэтому cookie и SSE работают с одного адреса.
- **Ядро — весь бэкенд**, одно приложение Nest из модулей. `core/src/app.module.ts` — их список.
  - `AuthModule` — вход и сотрудники. Вход: JWT в httpOnly-cookie `hb_access` и `hb_refresh` или `Authorization: Bearer`. Роли `USER`, `MANAGER`, `ADMIN`.
  - `EventsModule` — события в Redis и SSE `/api/stream`.
  - `PrismaModule` — доступ к базе.
  - `HealthModule` — `GET /api/health`.
  - Предметные модули `scenarios`, `gamification`, `analytics` подключаются туда же.
- **Модули ядра общаются** через экспортированные сервисы и через события (стрим `events` в Redis).

## Контракты — не нарушать

- **API:**
  - пути модуля — `/api/<name>/...`;
  - ошибки `{"code","message"}` с кодом в UPPER_SNAKE_CASE, валидация — `422 VALIDATION_ERROR`;
  - списки `{items, total}`, JSON в camelCase, даты ISO 8601 в UTC, идентификаторы — UUID.
- **База** — [docs/database.md](docs/database.md), там же правила для агентов:
  - одна схема `public` и роль `core_svc`; у каждого модуля ядра свои таблицы с префиксом модуля;
  - модули не пишут в таблицы друг друга напрямую и не связываются связями Prisma и JOIN. Данные другого модуля берутся через его сервис или копию из событий;
  - миграции — только новые и по одной, применённые не редактировать;
  - данные удаляются (`down -v`, `DROP`, `TRUNCATE`, `migrate reset`) только с согласия человека.
- **События** — [docs/events.md](docs/events.md):
  - один стрим `events`, конверт `{id, type, source, time, userId?, broadcast?, requestId?, data}`;
  - публикация — `EventsService.publish`; читает группа `core` с повторами и `events:dlq`;
  - обработчики идемпотентны;
  - ключи модуля в Redis — только `<name>:*`.
- **Уведомление пользователю** — событие `notification.requested` с `userId` или `broadcast: true`. Ядро само доставит его в браузер.
- **Контракты меняются** только в `docs/` и только по согласованию команды.

## Особенности версий — частые ошибки агентов

- **Nest 12 работает в ESM.** Относительные импорты пишутся с `.js` (`./app.module.js`).
- **Prisma 7:**
  - конфиг — `core/prisma7.config.ts`;
  - клиент генерируется в `core/src/generated/prisma`, импорт — `../generated/prisma/client.js`, не `@prisma/client`;
  - подключение — только через `@prisma/adapter-pg`;
  - `importFileExtension = "js"` в схеме не убирать: без него контейнер ядра падает при старте;
  - новая миграция: `npx prisma migrate dev --name <имя>` в `core/`, нужен `DATABASE_URL` на локальную базу.
- **Next 16:**
  - `middleware` переименован в `proxy` (`web/src/proxy.ts`);
  - перед правками читать документацию в `web/node_modules/next/dist/docs/`;
  - rewrites фиксируются при сборке, поэтому адрес ядра в Docker передаётся build-аргументом `CORE_URL`.
- **shadcn/ui в стиле `base-nova` построен на Base UI, а не на Radix:**
  - вместо `asChild` — проп `render={<Button />}`;
  - `cn` берётся из `@/lib/utils`;
  - новые компоненты добавлять командой `npx shadcn@4 add <name>`.
- **ioredis 6 и Redis 8 (RESP3):** ответ `XREADGROUP` может прийти как `[stream, entries]`, а не `[[stream, entries]]`. Разбор должен понимать обе формы: так работает `entriesOf` в `core/src/events/events.consumer.ts`, упрощать его нельзя.
- **Шрифт** — из пакета `geist`, а не `next/font/google`: сборка не должна зависеть от интернета.
- **`package-lock.json` в `core/` и `web/` должен подходить для `npm ci` в Linux.** Если npm на Windows пропустил платформенные пакеты, пересобрать lock в `node:24-alpine` командой `npm install --package-lock-only`.

## Команды

- Запуск: `docker compose up -d --build`.
  - `--wait` не использовать: Compose считает ошибкой `Exited (0)` у `db-init`.
  - статусы: `docker compose ps -a`; логи: `docker compose logs -f <сервис>`.
- Проверки в `core/` и `web/`: `npm test`, `npm run lint`, `npm run build`.
- События:
  ```bash
  docker compose exec redis redis-cli -a redis_pass --no-auth-warning XRANGE events - +
  ```
  Также полезны `XINFO GROUPS events`, `XPENDING events <группа>`, `XRANGE events:dlq - +`.
- Демо-аккаунты: `admin` / `admin123`, `manager` / `manager123`, `user` / `user123`.

## Как проверять изменения

- **После правок** прогнать тесты, линтер и сборку затронутого сервиса.
- **Поведение проверять на живом стеке.** Проверки, которые ломают данные или останавливают сервисы (падение базы или Redis, короткий `ACCESS_TTL`), — во временной копии проекта: `docker compose -p hbverify …` со своими портами (`POSTGRES_PORT`, `CORE_PORT`, `REDIS_PORT`, `WEB_PORT`). После проверки копию удалить через `down -v`.
- **`docker compose down -v` на основном стеке удаляет все данные** — только с согласия человека.
- **Результат сообщать честно:** что проверено, что нет, что упало.

## Windows — основная ОС команды

- **HTTP-запросы из PowerShell.** `curl` там — это `Invoke-WebRequest`, поэтому пишите `curl.exe`. Для JSON удобнее `Invoke-RestMethod`: PowerShell 5.1 выбрасывает кавычки из JSON в аргументах внешних программ.
- **Кириллица в теле запроса.** Передавайте её из файла в UTF-8 (`--data-binary "@body.json"`) или с `charset=utf-8` в `Content-Type`: в аргументах командной строки она искажается.
- **Пути в Git Bash.** Git Bash превращает пути вида `/tmp/...` в аргументах `docker` в Windows-пути. Используйте относительные пути внутри контейнера или `MSYS_NO_PATHCONV=1`.
- **Переводы строк — LF** (задано в `.gitattributes`). Shell-скрипт с CRLF в контейнере не запустится.

## Данные и безопасность

- **Только синтетические данные.** Никаких реальных ФИО, телефонов и табельных номеров — этого требуют 152-ФЗ и ТЗ.
- **Реальные секреты в репозиторий не класть.** Значения в `docker-compose.yml` и `.env.example` — только для разработки.
- **Порты сервисов открыты только на `127.0.0.1`** — так и оставлять.

## Язык и стиль

- **На русском:** общение, документация, комментарии в коде, тексты для пользователя, `message` в ошибках API.
- **На английском:** идентификаторы, коды ошибок, сообщения коммитов.
- **Комментарии** объясняют, почему сделано так, а не пересказывают код.
- **Кто над чем работает** — в разделе «Бэкенд и фронтенд».
